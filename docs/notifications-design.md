# 알림

## 합의한 동작

계정 옆 종 아이콘에서 미확인 숫자(최대 `99+`)와 최신순 알림 목록을 제공한다. 로그인·화면 경로 이동·목록 열기/닫기에 숫자를 조회하고, 목록 열기와 경로 이동에 목록을 조회한다. 팝업, 주기적 조회, SSE/WebSocket은 사용하지 않는다. 목록을 여는 것만으로 읽음 처리하지 않는다. 알림 클릭은 개별 읽음, ‘모두 읽음’은 현재 사용자의 미확인 알림 전체를 읽음 처리한다. 관리자 계정도 같은 알림을 사용할 수 있다.

| 종류 | 수신자 | 취소/삭제 |
| --- | --- | --- |
| 리뷰 좋아요 | 리뷰 작성자 | 좋아요 취소 시 제거 |
| 팔로우 | 팔로우 대상 | 팔로우 해제 시 제거 |
| 리뷰 숨김 | 리뷰 작성자 | 실제 공개→숨김 전환 시 한 번 생성, 신고 내용과 신고자 비공개 |
| 리뷰 댓글 | 리뷰 작성자 | 해당 댓글 삭제 시 제거 |
| 리뷰 답글 | 리뷰 작성자 + 원댓글 작성자 | 해당 답글 삭제 시 제거 |
| 댓글·답글 좋아요 | 해당 댓글·답글 작성자 | 좋아요 취소 또는 해당 댓글·답글 삭제 시 제거 |

행동한 본인은 제외한다. 수신자 집합으로 중복을 제거한다. 알림은 개별 행동 단위이며 묶지 않는다. 취소 후 재행동은 새 미확인 알림을 만든다. 기존 리뷰 자기 좋아요 기능은 유지하지만 자신의 알림은 만들지 않는다. 최초 배포 전 활동은 소급하지 않는다.

리뷰/계정 삭제 때문에 대상에 접근할 수 없게 되면 알림은 보존하되 이동 링크 대신 안내를 표시한다. 탈퇴한 행동자는 ‘탈퇴한 사용자’로 표시한다. 댓글 자체 삭제는 위 표의 명시적인 취소 정책을 따른다. 원댓글 삭제로 답글까지 삭제하지는 않으므로 답글 알림도 유지한다. 리뷰 삭제로 댓글이 일괄 정리되면 그 활동 알림은 접근 불가로 남는다.

숨김 알림을 클릭하면 게임명·처리 시각·‘작성하신 리뷰가 신고 검토 후 숨김 처리되었습니다’를 표시한다. 일반 리뷰 조회로 이동하지 않는다. 신고자의 주장을 관리자의 공개 사유처럼 사용하지 않는다. 댓글/답글 알림은 게임 화면의 기존 리뷰 카드로 스크롤하고 댓글창을 연다. 별도 알림용 리뷰 카드는 만들지 않는다. 내 리뷰는 첫 페이지 맨 위에 표시된다. 대상 리뷰가 현재 페이지에 없으면 조회 후 동일한 리뷰 목록에 중복 없이 포함한다. 대상 댓글은 별도로 조회하므로 댓글 페이지 순서가 바뀌어도 확인 가능하며 스포일러 보호를 유지한다.

## 저장과 API

`NotificationRequested`, `NotificationCancelled`, `CommentNotificationsCancelled`를 기존 서비스 트랜잭션 안에서 발행한다. 동기 이벤트 리스너가 같은 트랜잭션에 저장/삭제한다. 알림 실패 시 원래 행동도 롤백한다. 알림 저장을 `AFTER_COMMIT`으로 옮기면 원래 행동만 저장되고 알림은 누락될 수 있으므로 단순 변경하지 않는다.

`notifications`는 수신자, 행동자, 종류, 대상 종류/ID, 리뷰 ID, 게임명 스냅샷, 발생 시각, 읽음 시각, 원인 키를 저장한다. 대상/사용자 ID에는 외래 키를 두지 않아 삭제 후에도 안내 기록을 보존한다. `(source_key, recipient_id)` 유일 제약이 같은 활동의 중복 생성을 방지한다. 좋아요·팔로우·댓글 원인 키는 기존 관계를 식별하며, 숨김 원인 키에는 리뷰 버전이 포함된다.

모든 API는 인증된 사용자만 접근할 수 있다. 수신자 ID를 요청으로 받지 않고 로그인 사용자 ID로 제한한다.

- `GET /api/v1/notifications?before={id}&unreadOnly={boolean}`: ID 내림차순 20개, `items`와 `nextCursor` 반환. 조회 자체는 읽음 처리하지 않는다. `unreadOnly`의 기본값은 false이며 true이면 서버에서 미확인 알림만 필터링한 뒤 20개씩 조회한다. 필터를 바꾸면 첫 페이지부터 조회하고 ‘더 보기’에도 필터를 유지한다.
- `GET /api/v1/notifications/unread-count`: 미확인 개수.
- `PUT /api/v1/notifications/{id}/read`: 자신의 알림만 읽음 처리, 현재 접근 가능한 이동 정보 반환. 타인의 알림은 404.
- `PUT /api/v1/notifications/read-all`: 자신의 알림 전체 읽음.

프론트는 기존 `/api/review-api/notifications` 프록시와 토큰 갱신 방식을 사용한다. 목록/읽음 응답의 링크는 요청 시 대상 상태를 확인한다. 확인 직후 대상이 삭제되는 경우 대상 화면에서도 접근을 거부한다. 목록의 대상/행동자 조회는 페이지 크기 20으로 제한되어 있으며, 트래픽 증가 시 일괄 조회로 최적화할 수 있다.

운영은 `ddl-auto=validate`이므로 배포 전에 `docs/sql/notifications.sql`을 적용한다. 개발 `update`로 이미 생성된 DB에는 중복 실행하지 않는다. 이 작업은 SQL 파일만 제공하며 운영 DB에는 적용하지 않는다.

## 게시판 담당자 연결 방법

게시판 도메인은 아직 없으므로 게시판 테이블, 컨트롤러, 가상 서비스를 만들지 않는다. 게시판 구현 시 아래 지점만 확장한다.

1. `NotificationKind`에 `POST_LIKE`, `POST_COMMENT` 등 확정한 종류를 추가한다. `NotificationTarget`에 게시글/게시판 댓글 대상을 추가한다.
2. 실제 새 좋아요/댓글이 저장되는 트랜잭션에서 `ApplicationEventPublisher.publishEvent(NotificationRequested(...))`를 호출한다. 수신자는 게시글 작성자, 행동자는 좋아요/댓글 작성자다. 본인 제외와 수신자 중복 제거는 알림 서비스가 담당한다.
3. 원인 키는 `post-like:{postId}:{actorId}`, `post-comment:{commentId}`처럼 다른 도메인과 충돌하지 않게 만든다. 취소 시 동일 키의 `NotificationCancelled`를 발행한다. 댓글 삭제로 댓글 좋아요까지 지워야 한다면 리뷰 전용 취소 이벤트를 재사용하지 말고 해당 대상 종류의 취소 이벤트/처리를 추가한다.
4. `NotificationService.item`의 대상 판별에 게시판 조회/삭제 상태와 실제 이동 URL을 추가한다. 클라이언트가 임의 URL을 주입하는 API는 만들지 않는다.
5. 프론트 `api.ts`의 종류와 문구를 추가하고 수신자·취소·삭제·권한 통합 테스트를 추가한다. 게임명이 없는 게시판 알림은 `gameTitle=null`, `reviewId=null`을 사용한다. 게시글 제목이 필요하면 독립적인 스냅샷 필드를 추가한다.

공개 생성 API를 통해 사용자가 수신자/문구를 임의 지정하지 않는다. 알림 서비스는 기존 리뷰/사용자 서비스에 의존하지 않아 순환 참조를 만들지 않는다.

## 나중에 실시간 전달

현재의 DB/조회/읽음 API는 유지한다. DB 저장 트랜잭션이 커밋된 뒤 SSE로 ‘알림 변경’ 신호를 보내고 프론트가 기존 개수/목록 API를 다시 조회하도록 확장할 수 있다. 알림 저장은 현재 트랜잭션 안에 유지한다. 재접속 때는 반드시 DB에서 다시 조회해 연결이 끊긴 동안의 변경을 복구한다. 단일 프로세스의 커밋 후 신호는 유실될 수 있으므로 전달 보장이 필요할 때 outbox와 다중 서버 전달 수단을 별도 설계한다.

## 보관 정책과 자동 삭제

| 알림 | 삭제 기준 |
| --- | --- |
| 읽은 일반 알림 | 최초 읽음 시각부터 7일 경과 |
| 미확인 일반 알림 | 발생 시각부터 30일 경과 |
| 리뷰 숨김 알림 | 읽음 여부와 무관하게 발생 시각부터 90일 경과 |

미확인만 보기에서도 최신순을 유지한다. 알림을 읽으면 미확인 목록에서 바로 제거하고, ‘모두 읽음’은 필터와 무관하게 로그인 사용자의 미확인 알림 전체에 적용한다. 이미 읽은 알림을 다시 눌러도 최초 읽음 시각은 변경하지 않으며, ‘모두 읽음’ 역시 기존 읽음 시각을 갱신하지 않는다.

`NotificationCleanupScheduler`가 매일 새벽 4시 15분(Asia/Seoul)에 정리한다. 기간이 지난 알림은 다음 정리 시 삭제되므로 보통 최대 하루 늦게 삭제될 수 있으며, 서버 중단 시 재기동 후 다음 실행에 정리한다. 리뷰 숨김 알림은 일반 알림의 7일·30일 조건에서 명시적으로 제외한다. 리뷰의 숨김 상태와 신고 기록은 삭제하지 않는다.

대량 삭제로 긴 트랜잭션을 잡지 않도록 1,000건씩 별도 트랜잭션으로 삭제하며, 한 실행은 최대 100회(10만 건) 처리한다. 초과한 누적분은 다음 실행에서 정리한다. 삭제문이 현재 읽음 여부와 시각을 함께 검사하므로 후보 조회 후 읽음 상태가 바뀐 알림을 잘못 지우는 경로를 만들지 않는다. 미확인 숫자는 삭제된 행을 다음 조회부터 제외한다.

이미 알림 테이블이 생성된 운영 DB에는 `docs/sql/notification-retention.sql`을 한 번 적용해 정리용 인덱스를 추가한다. 신규 DB에는 최신 `notifications.sql`만 적용한다. 두 파일을 연달아 실행하지 않는다. 개발의 `ddl-auto=update`로 인덱스가 이미 추가된 DB에도 중복 적용하지 않는다.

사용자별 알림 설정과 묶음 표시는 이번 범위에 포함하지 않는다.

# GameLog 3차 프로젝트 기획서

상태: 협의 중인 초안. 아래 제안은 팀 합의 전까지 확정 요구사항으로 취급하지 않는다.

## 1. 프로젝트 배경과 목표

2차 GameLog의 Java 백엔드를 Kotlin으로 전환하고 기존 기능의 동작을 검증한다. 언어 변경 자체가 성능 향상을 보장한다고 가정하지 않으며, 코드의 명확성과 null 처리 개선은 구체적인 전환 사례로 설명한다.

확정된 작업 방향:

- 전환 대상 전체를 Kotlin으로 바꾼 결과를 한 번에 반영한다.
- 합의와 기획 문서는 `migration/`에서 공유한다.
- 운영 Java 코드 전체만 전환하며 테스트 코드는 Java로 유지한다.
- `/api/v1` 경로·요청·응답·인증·오류·DB 구조·데이터와 비즈니스 로직을 유지한다.
- 이번 범위는 마이그레이션만이다. 관리자 추천 갱신 기능은 제외하고 이후 별도로 검토한다.

## 2. Target User 및 사용자 시나리오 — 제안

| 대상 | 필요 | 대표 시나리오 |
|---|---|---|
| 게임 이용자 | 게임 탐색과 플레이 기록 관리 | 게임 탐색 → 상세 확인 → 기록·평가 → 맞춤 추천 확인 |
| 운영 관리자 | 기존 게임 데이터 관리 | 관리자 로그인 → 기존 IGDB 동기화 실행·상태 확인 |

기존 기능의 사용자 흐름을 보존하며 신규 관리자 추천 갱신 시나리오는 이번 범위에서 제외한다.

## 3. 기존 프로젝트 분석

- 기존 Java 코드와 핵심 API·DB 관계·테스트·실행 경로를 분석하여 전환 목록을 작성한다.
- 2026-10-22 사전 조사: 백엔드 운영 Java 232개, 테스트 Java 72개. 최종 범위를 정한 뒤 착수 시점에 다시 집계한다.
- JPA 엔티티·복합키, Lombok, Java record, JSON 직렬화, 검증 애너테이션, 트랜잭션·커밋 후 이벤트 및 추천 CLI를 중점 점검한다.
- 시스템 구성은 기존 구성과 달라지는 부분을 확인한다. 큰 변경이 없으면 과제 지침에 따라 구성도는 생략하거나 기존 자료를 참조한다.
- 기존 구성은 Next.js 프론트·API 프록시 → Spring Boot API → MySQL이며 IGDB·DeepL·Cloudinary를 연동한다. 로컬 Prometheus·Grafana와 추천 k6 스크립트도 존재한다.
- 기존 관리자 기능은 IGDB 게임 동기화 실행·상태 확인이다. 이번에 제안하는 추천 후보 갱신 관리와 구분한다.
- `.github/workflows/ci.yml`에 push·pull request 시 Java 25로 Gradle build를 수행하는 CI가 이미 있다. CI 신규 도입보다 Kotlin 전환 후 기존 CI 유지·검증 보완으로 계획한다.

## 4. Java → Kotlin 전환 대상 및 예상 효과

| 대상 | 전환 내용 | 확인할 효과 또는 유지 조건 |
|---|---|---|
| DTO | record·클래스를 Kotlin 표현으로 전환 | 반복 코드 감소, 기존 JSON·검증 결과 유지 |
| Controller·Service | 생성자 주입·프로퍼티·null 처리 적용 | 의존성과 필수값 명확화, 인증·오류·트랜잭션 유지 |
| Entity·Repository | JPA 매핑·조회 결과 타입 전환 | DB 구조·데이터·지연 로딩·복합키 동작 유지 |
| 설정·보안·외부 연동·CLI | Kotlin 전환과 실행 구성 조정 | 서버 기동·인증·연동·수동 명령 동작 유지 |
| 테스트 | Kotlin 전환 제외, Java 유지 | 호출 호환성의 최소 수정만 허용하고 변경 이유·전후 호출을 기록. 검증 내용·기대값 유지 |

운영 Java 코드 전체를 전환하고 테스트 Java 코드는 유지한다. Kotlin·JVM 버전과 플러그인은 호환성 확인 후 결정한다.

Java 25·Spring Boot·DB·주요 라이브러리 버전은 유지한다. Kotlin 지원에 필요한 설정을 추가하며, 기존 버전 변경이 불가피하면 근거와 함께 재협의한다.

## 5. 추가 구현 기능

이번 마이그레이션에는 신규 기능을 포함하지 않는다. 관리자 추천 갱신 화면은 이후 별도 검토한다.

| 트랜잭션·이벤트 동작 변화 | 실패 롤백·커밋 후 실행·기존 결과 보존 검증 |

## 7. 테스트 및 AI 활용 검증 — 제안

완료 시 clean build, 기존 Java 테스트, 서버 기동, 주요 API와 추천 CLI 동작을 검증한다. Q14에 따라 성능은 수치 기록만 하고 마이그레이션 완료의 통과·실패 기준으로 삼지 않는다. 성능 개선·회귀 판단과 반복 측정은 추후 검토한다.

- 단위: 점수 계산, 순위 재산정, 입력·상태 전환 등 독립 로직
- 통합: JPA·MySQL, 트랜잭션 롤백, 추천 갱신·공개 조건, 인증·직렬화
- API/E2E: 실제 서버 요청으로 주요 사용자 흐름 확인. 서버 내부 호출 테스트와 전체 시스템 E2E는 범위를 구분하여 기록
- 성능: 기존 k6 시나리오를 재사용하여 P95·P99·실패율·처리량 비교
- AI 검증 근거: AI가 작성한 변경 범위, 사람이 검토한 테스트, 실제 실행 결과를 구분하여 기록. 결함 주입 검증은 수행한 경우에만 근거로 기재

기존 Java 단계의 추천 사전 계산 성능 개선은 기존 성과로 분리한다. 그 개선율을 Kotlin 마이그레이션의 효과로 표현하지 않는다. 스크린샷 추정치와 원본 측정값도 구분한다.

## 8. 협업 및 개발 순서 — 제안

1. 범위·기준 동작·완료 기준 합의 및 Java 기준 검증 결과 확보
2. Kotlin 빌드 구성·전환 규칙 확정
3. 운영 코드 전체 전환 및 기존 Java 테스트로 검증
4. 하나의 통합 전환 결과를 PR 리뷰 후 반영
5. 기획 대비 결과·위험 대응·검증 근거 정리

일괄 전환은 최종 반영 범위를 의미한다. 에이전트가 커밋을 분리·실행하고 기록하며, 전환 기간의 대상 기능 수정은 미룬다. 전환 PR을 되돌려 Java 버전으로 복구할 수 있게 코드·빌드 변경을 관리한다. 일정·담당자·구체적인 CI 보완과 복구 검증 방법은 구현 계획에서 정리한다.

## 9. 범위 합의 (2026-10-22)

- Q1: 테스트 코드는 Kotlin 전환에서 제외하고 Java로 유지한다.
- Q2: 기존 API·인증·오류·추천 정책·DB 구조와 데이터를 유지한다.
- Q3: 비즈니스 로직을 변경하지 않는다.
- Q4: 관리자 신규 기능은 이후 검토하며 이번에는 마이그레이션만 진행한다.
- Q5: Java 테스트는 호출의 최소 수정만 허용한다. 파일·이유·전후 호출은 `README.md`에 기록하고 검증 내용·기대값은 유지한다.
- Q6: 기존 Java 25·Spring Boot·DB·주요 라이브러리 환경을 유지하고 Kotlin 지원 설정을 추가한다. 불가피한 버전 변경은 재협의한다.
- Q7: clean build·기존 Java 테스트·서버 기동·주요 API·추천 CLI를 검증한다. 성능은 이후 Q14에 따라 기록 대상으로 구분한다.
- Q8: 기존 DB·요청·외부 API의 null 허용 범위를 유지하고 필수값만 non-null로 표현한다. 무분별한 `!!`나 임의 기본값으로 컴파일 문제를 숨기지 않는다.
- Q9: DTO는 호환성을 확인하여 `data class`를 활용하고, JPA 엔티티는 일반 `class`로 기존 동등성·지연 로딩 동작을 보존한다. 복합키의 기존 값 비교 계약도 유지한다.
- Q10: 기존 서버 실행·환경변수·추천 CLI 명령을 유지하고 내부 진입점 변경은 빌드 설정에서 반영한다. 불가피한 외부 실행 방식 변경은 별도 협의·문서화한다.
- Q11: 전환 대상 기능 수정은 마이그레이션 완료 이후로 미룬다.
- Q12: 에이전트가 검토 대기 없이 커밋까지 수행하고 변경·검증 결과를 문서에 남긴다. push·병합은 별도 요청 범위이다.
- Q13: 별도 `BASELINE.md`에 현재 Java 기준 결과와 전환 후 비교 조건을 기록한다.
- Q14: 성능은 기록만 하고 평가·개선은 추후 검토한다. 성능 수치를 전환 완료의 통과·실패 기준으로 삼지 않는다.
- Q15: 기존 테스트 실패 시 구현의 호환성을 우선 수정한다. 테스트 삭제·비활성화·기대값 변경은 허용하지 않고 최소 호출 수정만 기록한다.
- Q16: DB 구조·데이터를 유지하고 전환 PR의 코드·빌드 설정을 되돌려 Java 버전으로 복구할 수 있게 관리한다.

사용자 의사결정 질문 Q1~Q16은 합의 완료이다. 기술 호환성 확인과 구체적인 실행 계획을 정리한 뒤 구현 시작 여부를 확인한다.
